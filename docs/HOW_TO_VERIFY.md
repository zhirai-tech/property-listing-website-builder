# 如何验证这个平台

面向**接手这个项目的人**（也包括三个月后的我自己）。

这个仓库已经有相当多的验证手段，但它们散在 `package.json` 与二十多份阶段报告里。
本文回答三个问题：**跑哪个、覆盖什么、失败了意味着什么。**

---

## 一、三十秒版本

```bash
pnpm install
pnpm typecheck     # 类型检查，不依赖服务，秒级
pnpm test          # 418 个单元/集成测试，不依赖服务
pnpm verify        # 45 项端到端走查，自己起临时环境，一条命令跑完
```

三条全绿 = 这次改动没有明显破坏。**三条的定位完全不同，见第三节。**

想手动看界面：

```bash
pnpm start         # http://127.0.0.1:3210
# 平台入口  /app/       （终端用户：注册、生成、下载、发布）
# 后台入口  /admin/     （运营者：房源、模板、备份）
```

## 二、全部命令一览

| 命令 | 覆盖什么 | 需要服务在跑 | 会写数据 |
| --- | --- | --- | --- |
| `pnpm typecheck` | 类型正确性 | 否 | 否 |
| `pnpm test` | 418 个单元/集成测试：领域逻辑、服务、路由、安全 | 否 | 否（临时文件库，跑完即删） |
| `pnpm verify` | **45 项端到端走查**（临时环境，自己起服务） | 否（自己起） | 临时目录，跑完即删 |
| `pnpm walkthrough` | 同上，但对着**已经在跑的**服务 | **是** | **真实库**（会自清理，但强杀时需自愈） |
| `pnpm smoke` | 端到端冒烟：房源 → 发布 → 提醒 → 导出（74 项检查） | 否 | 临时目录 |
| `pnpm migrate` | 应用数据库迁移 | 否 | **是**（真实库，**没有二次确认**） |
| `pnpm seed` | 写入演示数据 | 否 | **是** |
| `pnpm reminders` | 手动跑一次提醒投递扫描 | 否 | 是 |
| `pnpm expire-projects` | 归档到期的免费项目 | 否 | 是 |
| `pnpm dev` | 开发模式（文件变更自动重启，**同样会自动迁移**） | — | **是**（真实库结构） |

## 三、`pnpm verify` 与 `pnpm test` 的分工（**最重要的一节**）

这两者**不能互相替代**，混为一谈会导致两个错误结论。

### `pnpm test` —— 证明「每个部件按设计工作」

- 418 个测试，跑在**临时文件库**上（`os.tmpdir()` 下的 `pl-test-*`，跑完即删），不依赖服务、不依赖网络；
- 覆盖：领域逻辑、额度判定、用量台账幂等、校验门、权限、路径解析、导入导出；
- **快**（秒级），适合每次改动都跑，也适合放进 CI；
- **但它抓不到接缝问题。**

### `pnpm verify` —— 证明「这些部件接起来能完成一件完整的事」

- 45 项检查，跑在**真实服务 + 真实 HTTP + 真实数据库**上；
- 覆盖两条完整旅程：**自定义单页**（注册 → 生成 → 保存 → 预览 → 下载 → 发布 → 匿名访问 → 改草稿 → 停止托管 → 回收站）
  与**房源插件**（建房 → 照片 → 排序封面 → AI 修改 → 内容同步 → 导出 → 租户隔离）；
- 还覆盖既有功能：多语言展示页、提醒状态流转、备份创建与校验；
- **慢**（要起服务、要造数据），适合**交付之前**跑一次。

### 为什么必须两个都跑

前二十三个阶段的经验是：**真实缺陷几乎都长在接缝上。**

| 曾经的真实缺陷 | 类型 |
| --- | --- |
| 改草稿把线上页面直接下线 | 草稿保存 与 公开路由 的接缝 |
| 平台项目与房源展示页的短链撞车 | 两套 slug 空间 的接缝 |
| 上游返回空补丁却提示「成功」 | 上游 与 校验门 的接缝 |
| 照片区出现在没有房源的插件里 | 编辑器 与 插件清单 的接缝 |
| 「回收站」按钮的事件绑定丢失 | HTML 与 JS 的接缝 |
| 公开页周边信息 100% 失败并泄露内部错误 | HTTP 头 与 Node 的接缝 |

**这些缺陷在 412 个测试全绿的情况下全部存在过** —— 它们不是某个部件写错了，
而是两个部件的约定对不上。**接缝只能靠端到端跑。**

反过来，`pnpm verify` 也**不能**替代 `pnpm test`：
它慢、要求能起服务、不适合放进普通 CI job，而且它**不覆盖**大量的边界条件
（额度耗尽、并发、异常输入、路径编码变体……）。

## 四、`pnpm verify` 跑挂了怎么办

### 4.1 先看输出

它打印一张检查清单。失败项会列在最下面：

```
  [FAIL] 26. spec 同步到了房源记录（关键接缝）   title=… price=…
  ------------------------------------------------------------------------------------
  通过 44 / 45

  失败项：
    26. spec 同步到了房源记录（关键接缝）  title=… price=…
```

**退出码**：`0` 全过 · `1` 有检查失败 · `2` 脚本自身出错 · `130` 被 Ctrl+C 打断。

### 4.2 如果是「连不上服务」

`pnpm walkthrough` 需要服务已经在跑。提示会直接告诉你：

```
✖ 连不上 http://127.0.0.1:3210。请先在另一个终端运行 `pnpm start`。
```

**用 `pnpm verify` 就没有这个问题** —— 它自己起临时服务。

### 4.3 如果失败的是「既有功能」那一组

`pnpm walkthrough`（对着你自己的实例跑）会检查既有房源、展示页、提醒是否存在。
如果你的实例是**全新的空库**，这一组必然失败 —— **那是环境问题，不是缺陷**。
先跑 `pnpm seed`，或者直接用 `pnpm verify`（它会自动播种）。

### 4.4 如果它留下了垃圾

正常情况下不会：

- 临时目录跑完即删；
- 测试账号按 `walkthrough-` 前缀删除；
- 走查创建的备份文件会删掉。

如果上一次被**强杀**（Ctrl+C、断电），残留可能留下。
**下一次 `pnpm walkthrough` 启动时会自动清理**（按前缀扫一遍）。

手动清：

```bash
# 残留临时目录（Linux/macOS）
rm -rf "${TMPDIR:-/tmp}"/walkthrough-verify-*

# 残留临时目录（Windows PowerShell）
Remove-Item "$env:TEMP\walkthrough-verify-*" -Recurse -Force

# 残留账号：**直接再跑一次 pnpm walkthrough 就会自动清掉**
# （脚本启动时按 walkthrough- 前缀扫一遍），这是最省事的做法。
# 想手动清，见 scripts/walkthrough.ts 里 finally 块与启动时的清理逻辑。
```

## 五、**已知的失败与限制**（不看你可能会以为是自己搞坏了）

### 5.1 提醒的「第 7 天」是**日历日**，不是 168 小时

`pnpm smoke` 曾经固定失败，根因不是产品缺陷，而是**断言写错了**：

- 产品规则是「**发布当地日历日 + N 天，时刻为该时区的当地 09:00**」
  （`buildReminderPlan` → `addZonedDays` + `zonedHourOfDay`）；
- 旧断言却要求「瞬时差 ≥ N×24 小时」。

两者在两种常见情况下**并不相等**：

| 情况 | 当地日历日 | 当地时刻 | 瞬时差 |
| --- | --- | --- | --- |
| 发布在当地 09:00 **之前**（08:30） | +7 ✓ | 09:00 ✓ | **7.021 天** |
| 发布在当地 09:00 **之后**（18:00） | +7 ✓ | 09:00 ✓ | **6.625 天** |
| 跨越夏令时开始 | +7 ✓ | 09:00 ✓ | **6.958 天** |
| 跨越夏令时结束 | +7 ✓ | 09:00 ✓ | **7.042 天** |

所以旧断言**在一天中的大部分时间都会失败**（发布时刻晚于当地 09:00 时必然失败）。

**已修复**：断言改为按「当地日历日 +7 / +15」与「当地 09:00:00」验证，
复用产品自身的 `toZonedParts`。**产品规则没有任何改动。**

**给改代码的人**：判断「第 N 天」时**不要用毫秒差**——
要么复用 `toZonedParts` 比较当地日历字段，要么直接用 `addZonedDays`。
DST 切换会让瞬时差偏离 N×24 小时约 1 小时。

### 5.2 **默认配置下 AI 功能不可用**

默认 `AI_PROVIDER=mock` —— 一个不发网络请求、不花钱的实现。

**它生成不出页面。** 默认配置下点「AI 生成」会失败（但会明确告诉你原因，且**不扣额度**）。

要启用真实生成能力：

```bash
AI_PROVIDER=openai
AI_BASE_URL=https://<你的上游>/v1
AI_API_KEY=<密钥>
AI_MODEL=<模型名>
```

**启动日志与 `/api/admin/diagnostics` 都会明确告诉你当前是哪种状态**：

```
[AI] 当前使用内置的模拟 AI（mock）：不会发出任何网络请求、不产生费用，但无法真正生成网页。
     「自定义单页」功能在此配置下不可用。
[AI]   需要做：若要启用真实生成能力，设置 AI_PROVIDER=openai
[AI]   需要做：并同时提供 AI_BASE_URL / AI_API_KEY / AI_MODEL 三项
```

**注意**：本项目**从未接过真实 AI 供应商**（用户要求不调用真实付费服务）。
provider 的协议、错误处理、用量解析都已用**本地假上游**验证过，
但**「真实模型产出质量如何」完全未验证**。

### 5.3 公开页的「附近」区块拿不到数据

`/p/<slug>/nearby.json` 依赖 OSM 的公共服务，实测返回 **HTTP 406**（对方策略）。
现在会**优雅降级**并给出可读说明，页面本身不受影响。
**拿不到数据是正常现象**，不是你搞坏了。

（此前这里 100% 失败并**把 Node 的内部报错原样透给访客**，已在第二十二阶段修复。）

### 5.4 **启动服务就会迁移数据库**（不只是 `pnpm migrate`）

这一点容易漏：`src/db/migrate.ts` 的注释写着「同时作为模块被 server.ts 调用，
**保证启动即迁移**」。所以 `pnpm start` 和 `pnpm dev` **同样会改真实库结构**。

**好消息**：迁移全部是**追加式**的（新增表、新增列，带默认值），
不会清库、不会重建表、不会删列。截至目前 v1→v5 每次都在真实库的**克隆**上验证过「行数零丢失」。

**且 `pnpm migrate` 没有任何二次确认，也没有自动备份** —— 它直接执行。

所以：
- 跑之前先确认当前版本；
- **改迁移代码时，永远先在克隆库上验证**，不要拿真实库试。

当前迁移版本：**v5**（v1 初始结构 · v2 可租状态 · v3 平台基础 · v4 会话吊销 · v5 项目公开短链）。

## 六、改动之后该跑什么

| 你改了什么 | 最少要跑 |
| --- | --- |
| 任何 TypeScript | `pnpm typecheck` + `pnpm test` |
| 路由、权限、额度 | 上面两个 + `pnpm verify` |
| 数据库迁移 | 上面三个 + **在克隆库上先验证零丢失**（见下） |
| 前端界面 | `pnpm verify` + **真的打开浏览器点一遍** |
| AI / 插件 | `pnpm test` + `pnpm verify` |

### 迁移的验证方式

**永远不要直接在生产库上试新迁移。** 先复制一份再跑：

```bash
cp var/db/app.sqlite /tmp/clone.sqlite
# 对 clone 跑迁移，比对迁移前后每张表的行数与内容
```

第二十二、二十三阶段的报告里有可复用的脚本（`var/check-v3.mjs`、`var/check-v5.mjs`）。

## 七、`pnpm verify` 不能替代什么

**必须讲清楚，否则会被误用：**

1. **不能替代人工走查。** 浏览器交互、视觉排版、文案是否好懂 —— 仍然需要人看。
   它检查的是「数据对不对、状态对不对」，不是「看起来对不对」。

2. **不能替代真实用户测试。** 到现在为止**没有任何真实用户用过这个平台**。
   所有关于「引导文案是否易懂」「示例是否有帮助」的判断，都是我的推测。

3. **不能替代真实模型验证。** 它跑的是默认 `mock` 配置 ——
   验证的是「失败得是否正确」，**不是「真实模型能不能生成出可用页面」**。

4. **不能替代公网验证。** 所有验证都在 `127.0.0.1` 上做过，
   **从未部署到公网**（用户明确要求）。
