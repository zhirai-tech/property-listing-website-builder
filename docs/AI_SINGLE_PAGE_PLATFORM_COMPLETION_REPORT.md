### 关于「WAL 与 SHA256」这一条方法论

上一轮我发现：数据库是 **WAL 模式**，写入先落在 `app.sqlite-wal`（当前 **4.1 MB**），
主库 `app.sqlite` 的字节可以长时间不变。所以**用主库 SHA256 判断「数据库有没有变」是不可靠的** ——
上一轮就是主库 SHA256 一模一样、而库里确实多了一列。

本次一律改用：
- `PRAGMA journal_mode`（确认模式）
- `SELECT * FROM schema_migrations`（确认迁移状态与时间）
- `PRAGMA table_info(...)`（确认实际列）
- `PRAGMA foreign_key_check` / `integrity_check`（确认完整性）

### 4. 媒体资源访问控制 ✅（查清边界并固化）

**结论：现有机制是双层防护且正确的，我没有改它** —— `/media/*` 一旦加错鉴权，
**已发布页面的图片会全部失效**。

| 层 | 机制 |
| --- | --- |
| 路由 | 拒绝 `..`、`\0`、前导 `/`、空 |
| `assertSafeKey` | 拒绝绝对路径、盘符、`.`/`..`/空段、`\0` |
| `resolveKeyPath` | **复核**解析结果确实位于存储根目录内 |

| 验证项 | 结果 |
| --- | --- |
| 8 种穿越/编码变体（`../`、`..%2f`、`%2e%2e`、`....//`、`C:/`、`%00`、`//`、`./`） | ✅ 全部 400/404，且**不泄露数据库或系统文件内容** |
| 合法资源匿名可读（公开页面依赖它） | ✅ 200 |
| 不存在的 key → 404，**不泄露服务器路径** | ✅ |
| **storageKey 不可枚举**：第一段是房源 ID（可预测），第二段是足够长的随机码；用可预测部分猜 4 个常见名全部失败 | ✅ |
| 跨用户：B 读/删 A 的媒体列表 → 404 | ✅ |

**随机短码的作用与边界**（按要求先明确再决定）：
`<propertyId>/<随机码>.<ext>` —— 随机段是**唯一**的防枚举机制。
它的边界是：**知道完整 key 的人就能取到那张图**。这对「公开展示页要能加载图片」是必需的，
且分享出去的展示页本身已公开其中引用的图片，因此**自洽**。
本次**未改动**，仅固化边界。

### 7. 真实 AI Provider 链路 ✅（代码与模拟层面；**未调用任何付费服务**）

| 环节 | 状态 |
| --- | --- |
| 调用 | 已实现，`AbortSignal.timeout` 超时；**本次新增有界重试** |
| 响应解析 | `parsePatch` 处理代码块包裹的 JSON；`readUsage` 兼容各家字段差异 |
| **失败重试** | **本次新增**：只重试「确定没有产生生成结果」的失败 |
| 结果保存 | 补丁经 `checkSpec` 校验门 → `saveDraft` → 版本追加 |
| 额度扣减 | `claimTask`（`task_id` 唯一）→ `settleTask`；失败记 `failed`，**不计入额度** |

**重试的判据是「有没有可能已经产生了输出」，不是「错得严不严重」**（重试要花钱）：

| 失败类型 | 是否重试 | 理由 |
| --- | --- | --- |
| `network`（连接失败） | **重试** | 一定没生成 |
| `http` 502/503/504（网关） | **重试** | 模型通常还没开始生成 |
| `timeout` | **不重试** | 可能已经生成完只是回不来，重试=再花一次 |
| `protocol`（模型输出不合法） | **不重试** | 已经产出内容（已计费） |
| `usage_missing` | **不重试** | 重试只会累积更多「无法计费」的消耗 |
| `http` 4xx | **不重试** | 请求本身有问题 |

上限由 `PLATFORM_LIMITS.aiMaxRetries` 控制（默认 1）。
**幂等性**：整次任务共用同一个 `taskId`，结算只发生一次。

**用本地假上游验证（零付费调用）**：
- 连接失败 → **重试并成功**，`hits === 2`，台账**只有一条**记录、只记成功那次的用量 ✅
- 超时 → **只请求一次**（`hits === 1`）✅
