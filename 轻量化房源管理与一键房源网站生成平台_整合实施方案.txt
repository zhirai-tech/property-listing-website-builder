轻量化房源管理与一键房源网站生成平台
整合实施方案（归档稿 1.0）

用途：长期保存，后续按阶段排队实施
当前状态：仅规划，不立即开发

一、项目目标

建设一个轻量化的房源管理与发布工具。用户只需录入一次房源信息并上传照片/视频，系统即可生成可分享的房源展示页面。后续逐步支持地图与周边信息、多语言、多套房源管理、HTML 导出、子域名托管以及发布后的状态提醒。

基本原则：
1. 简单轻量，优先评估成熟开源项目，不重复造轮子。
2. 只选择一个主系统作为底座，其他项目只补充必要能力或作为设计参考，不直接拼接多个完整系统。
3. 房源信息只维护一份，后台、展示页和导出内容均从统一数据源生成。
4. 面向国内外通用场景，避免将某一国家的地址、货币、费用规则写死。
5. 按阶段实施，每阶段完成真实用户路径测试和验收后再进入下一阶段。
6. 商用前核实主项目、依赖、模板和媒体素材的许可证及授权情况。

二、开源项目整合策略

1. PropertyWebBuilder：主底座优先评估对象。
重点核对房源展示、后台管理、多房源组织、地图、多语言、部署方式、技术栈、数据模型、维护状态及许可证。通过实际拉取代码和部署测试后，才能最终决定是否采用，不能仅凭项目介绍直接定案。

2. OpenProperty：后台管理能力参考。
当主底座的房源录入、管理流程或数据组织能力不足时，再参考其实现。优先复用可合法使用的独立组件或设计思路，不默认把整套后台与主底座合并，避免重复登录、重复数据模型和额外维护负担。

3. real-estate-listing-template：单套房源页面模板参考。
用于参考房源详情页的视觉结构、信息分区和响应式布局。需单独核对代码许可证和示例照片的版权；模板代码可用不代表其中图片可以商用。

4. MicroRealEstate：暂不作为核心依赖。
在确认当前许可证、托管条款和目标商业模式兼容之前，不把它作为平台核心。只有在完成条款核验后，才考虑使用其中可合法采用的能力。

重要说明：以上为方案阶段的候选分工，不代表已经完成许可证审查、兼容性验证或生产部署。实施时必须以官方仓库当前代码、LICENSE、依赖清单和实际测试结果为准。如果候选项目不符合需求，应提供证据和替代方案，再决定是否更换底座。

三、产品功能范围

1. 房源录入与编辑
包括标题、描述、地址/区域、房型、面积、价格或租金、押金、附加费用、可入住日期、联系方式、房源状态等。字段应可配置，避免将特定国家的规则写死。

2. 照片与视频管理
支持上传多张照片、调整顺序、指定封面；可选支持视频文件或外部视频链接。对文件类型、大小和数量进行校验，并记录素材来源或授权说明。

3. 一键生成展示页面
根据房源记录生成适配手机和桌面的详情页，提供预览、发布/撤下、唯一分享链接及二维码等能力。修改房源信息后，展示页应能同步更新。

4. HTML 静态导出
可导出 HTML 页面及所需静态资源，便于用户自行保存或部署。应说明地图、在线字体或其他外部服务在离线环境下可能无法完整运行。

5. 多房源管理
提供房源列表、搜索、筛选、编辑、复制、上下架和归档，避免重复录入相同房源。

6. 地图与周边信息
展示房源位置，并逐步支持附近交通、商店、学校等周边信息。地图接入采用可替换的适配层，按国家/地区配置服务和密钥。上线前明确免费额度及潜在费用。

7. 多语言与国际化
支持多语言界面、房源描述翻译、货币/日期/面积单位格式配置。原始描述与翻译文本应分开保存，切换语言不能覆盖原文。

8. 托管发布与子域名
先支持平台默认发布地址，再逐步支持自定义子域名、域名绑定、HTTPS、发布撤回和故障提示。域名需完成所有权验证，不能直接绑定未经验证的域名。

9. 发布状态提醒
发布后第 7 天提醒检查房源，第 15 天提醒确认或更新。提醒规则、时区和通知方式应可配置，并允许用户关闭或标记完成。

10. 权限与隐私
房源由所有者或获授权的管理者操作。联系方式应允许用户决定是否公开。提供撤下页面、删除素材、删除或导出数据等基本能力。

四、建议的核心数据结构

所有展示页和导出内容均从统一房源数据生成，不得在多个模块各自维护互不一致的副本。

1. Property（房源）：内部 ID、标题、描述、地址/区域、经纬度、房型/面积、价格、费用说明、可入住日期、状态、创建时间、更新时间。
2. Media（媒体）：房源 ID、文件地址、媒体类型、排序、封面标记、素材来源或授权说明。
3. Contact（联系方式）：显示名称、电话/邮箱/聊天方式、公开策略。
4. ListingPage（发布页面）：房源 ID、公开 slug、语言、主题/模板、发布状态、发布时间。
5. Reminder（提醒）：房源 ID、提醒类型、计划时间、完成状态、时区。
6. User/Workspace（用户与工作区）：所有者、权限、默认语言、默认单位、托管配置。
7. ExternalServiceConfig（外部服务配置）：地图、存储、邮件等适配器类型与配置。密钥不能写入前端或提交到代码仓库。

以上是逻辑模型建议。正式开发前应先检查选定底座已有的数据模型，尽可能扩展和复用，而不是不经检查就新建一套重复结构。

五、分阶段实施队列

第 0 阶段：开源项目检查与底座定案
工作：检查候选项目的官方仓库、许可证、维护状态、技术栈、依赖、部署流程和数据模型；制作能力对照表并进行实际部署验证；最终只确定一个主底座。
交付与验收：项目选择记录、许可证核验清单、部署成功证据、未采用项目及原因。未完成本阶段，不开始业务功能开发。

第 1 阶段：最小可用房源管理
工作：房源新增、查看、编辑、删除或归档、状态切换、照片上传和封面设置；数据保存到统一数据库。
验收：使用真实浏览器完成完整操作；刷新后数据仍存在；错误输入有明确提示；不存在第二套重复数据模型。

第 2 阶段：一键生成房源页面
工作：从房源记录生成公开详情页，支持手机和桌面布局、预览、复制链接、发布和撤下。
验收：修改房源后页面同步更新；未发布房源不能被公开访问；后台与页面内容一致。

第 3 阶段：展示模板与 HTML 导出
工作：吸收经过许可核验的模板设计，提供模板选择和静态 HTML/资源导出。
验收：导出文件可在本地打开；图片路径有效；核心展示不依赖内部管理后台。

第 4 阶段：地图与周边信息
工作：加入地图定位及周边信息；地图服务通过统一适配层接入，支持后续替换服务商。
验收：位置准确；密钥安全；地图服务故障时仍可显示地址；说明服务额度和费用风险。

第 5 阶段：多语言与国际化
工作：支持多语言界面、翻译字段、货币/日期/面积单位格式配置。
验收：切换语言不丢失数据；原始描述不被翻译覆盖；格式按配置正确显示。

第 6 阶段：托管发布与子域名
工作：先实现默认托管地址，再支持自定义子域名或域名绑定、HTTPS、发布撤回和错误处理。
验收：完成域名所有权验证；HTTPS 有效；发布和撤回可以重复操作；未经验证的域名不能直接绑定。

第 7 阶段：第 7 天与第 15 天提醒
工作：加入可配置的定时提醒：发布后第 7 天提醒检查，第 15 天提醒确认或更新；支持时区、完成状态和关闭提醒。
验收：用可控测试时间验证规则，不需要真实等待 7/15 天；提醒可重试且不会重复轰炸用户。

第 8 阶段：安全、性能与上线准备
工作：检查权限隔离、上传文件校验、备份恢复、日志、错误提示、移动端体验、基础性能、许可证归档和部署/回滚步骤。
验收：关键用户路径通过真实浏览器测试；备份能够恢复；无硬编码密钥；上线与回滚流程清楚。

六、每阶段的统一开发规则

1. 一次只实施一个阶段；当前阶段未通过验收，不自动进入下一阶段。
2. 开始修改前先检查现有代码、数据库、API 和 UI，确认已有能力与真正缺口。
3. 优先复用现有模块和成熟依赖，不创建平行的 V2/Legacy 系统，不留下隐藏旧实现或重复模块。
4. 必须通过真实浏览器操作验证用户路径，包括点击、输入、提交、刷新和查看结果；不能只凭类型检查、单元测试或接口返回宣布完成。
5. 涉及数据库时，检查迁移、旧数据兼容、保存后读取、删除/归档和失败回滚。
6. 每阶段报告必须列出实际修改内容、运行方式、浏览器测试路径、通过项及证据、失败项、遗留问题和下一阶段建议。未经验证的内容不得报告为完成。
7. 如果主底座不能满足关键需求，先提交可核实的证据和替代方案，不得未经确认直接换框架或重做系统。
8. 所有外部服务都应有明确配置边界；密钥不得暴露在前端或提交进仓库。

七、首期暂不纳入的内容

1. 复杂 CRM、租约签署、支付、佣金结算和自动获客。
2. 同时运行多个完整后台并在它们之间同步数据。
3. 强绑定单一地图、存储、翻译或托管供应商。
4. 在许可证和图片素材授权未核验前直接商用发布。
5. 核心房源录入与展示闭环尚未稳定前，先做复杂营销或大规模多租户能力。

八、主要风险与控制措施

1. 许可证与商业限制：保存主项目、依赖、模板和媒体素材的许可证/授权证据；条款不明确时先暂停使用。
2. 开源项目状态变化：实施前重新检查官方仓库、版本、维护情况和安全公告。
3. 拼接导致复杂：始终只保留一个主底座，其余项目只补充有限、必要且合法可用的能力。
4. 地图或托管产生费用：外部服务采用可替换适配器；上线前明确免费额度、超额计费和责任归属。
5. 图片或联系方式泄露：仅公开用户明确允许公开的字段，并支持撤下页面和删除媒体。
6. 定时提醒不可靠：记录计划时间、执行状态和失败原因；支持安全重试并防止重复通知。

十、当前决策摘要

1. 当前仅保存方案，不立即开发。
2. 产品方向：轻量、国内外通用、一次录入、一键生成房源展示页。
3. 主底座：优先评估 PropertyWebBuilder，但必须经过第 0 阶段实际检查和部署验证后才能最终定案。
4. 补充参考：OpenProperty 用于后台能力参考；real-estate-listing-template 用于展示页面参考；MicroRealEstate 暂不作为核心依赖，先核实当前商业托管条款。
5. 实施顺序：开源项目核验与底座定案 → 房源管理 → 页面生成 → 模板与 HTML 导出 → 地图 → 多语言 → 托管与子域名 → 提醒 → 安全与上线准备。
6. 执行原则：每次只推进一个阶段，通过真实用户路径测试和验收后，再决定是否进入下一阶段。

方案备注：这是一份待实施规划，不是已完成开发或许可证审查的证明。后续实施时应重新核对所有开源项目的当前状态。
